# 온라인 멀티플레이 전환 계획 (계획만 — 미착수)

> 작성 2026-07-03. 실행 전 사용자와 아키텍처 선택(아래 결정 1~3) 합의 필요.

## 현재 구조와 전제

- **완전 클라이언트 게임**: 모든 룰이 `gameStore.ts`(Zustand) 액션으로 실행, 서버 없음.
  GitHub Pages **정적 배포**(Next.js static export) — 서버 코드를 넣을 곳이 없다.
- **턴제 + 저빈도 메시지**: 초당 수십 메시지가 아니라 "행동당 1메시지" 수준. 실시간 게임이 아니라
  동기화 난이도가 낮은 편.
- **유리한 기존 자산**: ① 모든 행동이 store 액션으로 일원화(= 직렬화 가능한 커맨드 후보),
  ② `growGoods(diceResults)`처럼 주사위가 이미 **파라미터 주입**, ③ persist로 상태 직렬화 검증됨,
  ④ 시뮬 테스트의 시드 RNG 인프라, ⑤ `logAction` 구조화 로깅.
- **걸림돌**: ① `initGame`/물품 성장 등 곳곳의 `Math.random` 직접 호출(결정론 깨짐),
  ② AI 실행이 클라이언트 타이머(`scheduleAICheck`) 기반, ③ undo가 로컬 전제,
  ④ 상대 행동의 실시간 반영 UI 없음.

## 결정 1 — 백엔드 방식 (권장: ②)

| 방식 | 장점 | 단점 |
|---|---|---|
| ① P2P (WebRTC, Trystero/PeerJS) | 서버비 0, GitHub Pages 유지 | 시그널링 의존, NAT 실패 케이스, 호스트 이탈 처리 복잡, 치팅 방어 불가 |
| ② **BaaS 실시간 채널 (Supabase Realtime / Firebase RTDB)** | 서버 코드 불필요·무료 티어 충분, 정적 배포 유지, 방/재접속 상태 저장 겸용 | 벤더 의존, 룰 검증은 여전히 클라이언트 |
| ③ 자체 WebSocket 서버 (Node + Socket.IO, Fly.io/Railway) | 서버 권위 검증 가능(치팅 방어 최상) | 호스팅 비용/운영, 룰 엔진을 서버로 복제 or 이전 필요 |
| ④ boardgame.io 프레임워크 이전 | 멀티·로비·리플레이 내장 | **전면 재작성 수준** — 기존 gameStore와 이중 구조, 비추천 |

친구끼리 플레이가 목표면 ②로 충분. 공개 랭킹/치팅 방어가 목표가 되면 그때 ③으로 승격
(②의 동기화 모델을 그대로 서버로 옮길 수 있게 설계해 둔다).

## 결정 2 — 동기화 모델 (권장: 호스트 권위)

- **호스트 권위(권장)**: 방장 클라이언트만 gameStore를 "진짜"로 실행. 게스트는 **의도(intent)**
  (예: `{type:'buildTrack', coord, edges}`)만 채널로 보내고, 호스트가 기존 액션으로 검증·실행 후
  **직렬화된 GameState 스냅샷**(persist 포맷 재사용, 수 KB)을 브로드캐스트. 게스트는 `setState`로 반영.
  - 장점: 결정론 불필요(랜덤은 호스트에서만 발생), 디싱크 원천 차단, **기존 코드 변경 최소**.
  - 단점: 호스트 이탈 시 승계 필요(스냅샷이 BaaS에 저장돼 있으므로 다른 플레이어가 이어받기 가능).
- 대안(락스텝: 액션만 전파, 전원 로컬 실행)은 트래픽은 적지만 `Math.random` 전면 시드화가 선행돼야
  하고 디싱크 디버깅이 고통 — 이 게임 규모에선 이득이 없다.

## 결정 3 — 범위

- 1차 목표: **친구와 2~6인 비공개 방** (방 코드 입장), AI 혼합 허용(AI는 호스트에서 실행 — 기존
  `scheduleAICheck` 그대로), 재접속 지원. 관전/채팅/매치메이킹은 후순위.

## 단계별 로드맵 (각 단계 = 커밋·푸시 + 게이트)

### M0. 엔진 선행 정리 (멀티 없이도 가치 있음, 1~2일)
- `Math.random` 직접 호출을 `rng()` 주입으로 통일 (`createInitialGameState`, 물품성장, 경매 셋업 등).
  시뮬 테스트의 시드 RNG를 그대로 쓰면 게이트 유지 가능.
- 사람 입력 액션을 **직렬화 가능한 intent 타입**으로 목록화 (이미 store 액션 시그니처가 사실상 그 목록 —
  `types/game.ts`에 `PlayerIntent` union 정의만 추가).
- 게이트: 전체 vitest + 100시드 베이스라인 불변.

### M1. 전송 계층 (2~3일)
- Supabase 프로젝트 + `rooms` 테이블(방 코드, 스냅샷 JSON, 갱신 시각) + Realtime 채널.
- `src/net/` 신설: `createRoom / joinRoom / sendIntent / broadcastSnapshot / onSnapshot` 5개 API로 추상화
  (**gameStore는 net을 모름** — 나중에 ③ 자체 서버로 갈아타도 net만 교체).
- 게이트: 두 브라우저에서 에코 왕복 확인.

### M2. 호스트 권위 루프 (3~5일, 핵심)
- 호스트: `onIntent → 기존 store 액션 호출 → (성공/실패 무관) 스냅샷 브로드캐스트`.
  검증은 이미 액션 안에 있음(canBuildTrack, 경매 검증 등) — 추가 룰 코드 없음.
- 게스트: 로컬 액션 실행 차단(자기 차례 UI만 활성) + `onSnapshot → setState`.
  `merge` 콜백의 1회성 상태 초기화 로직 재사용 주의 (CLAUDE.md persist 섹션).
- undo: **자기 차례 + 호스트 확정 전**으로 제한(스냅샷 브로드캐스트 전만 허용)이 단순안.
- 게이트: 2브라우저 튜토리얼 완주 + 헤드리스 시뮬(호스트 경로) 통과.

### M3. 방/로비/좌석 UI (2~3일)
- `/game/[mapId]`에 방 생성/코드 입장/좌석(사람·AI) 배정 화면, 대기실 → initGame은 호스트만.
- 차례 알림("당신 차례"), 상대 행동 로그 표시(기존 logs 재사용), 연결 상태 표시(`OfflineIndicator` 확장).

### M4. 재접속/호스트 승계 (2일)
- 스냅샷이 rooms에 저장되므로: 새로고침 → 방 코드로 재입장 → 최신 스냅샷 복원.
- 호스트 이탈 감지(하트비트) → 남은 첫 플레이어가 호스트 롤 인수(스냅샷에서 이어 실행).

### M5. 마감 (1~2일)
- 시각 검수, 느린 네트워크 시뮬, 문서화. (치팅 방어가 필요해지면 이 시점에 ③ 승격 검토)

## 리스크

- **정적 export 유지 가능**: Supabase는 클라이언트 SDK만으로 동작 — GitHub Pages 배포 불변.
  단 anon key가 공개되므로 RLS(Row Level Security)로 방 접근 제한 필수.
- AI 사고 지연(1초 setTimeout)이 호스트에서만 돌므로 게스트는 "AI 생각 중" 표시로 충분.
- 가장 큰 함정은 M2에서 **게스트가 로컬로 상태를 바꿔버리는 경로**(키보드 단축키, 애니메이션 완료 콜백
  `completeCubeMove` 등) — 게스트 모드 가드를 store 진입점(액션 최상단)에 일괄로 넣을 것.

## 예상 규모

순수 작업일 기준 약 2~3주. M0은 멀티 안 하더라도 코드 건강에 이득이라 선행 무방.
현재 진행 중인 리팩토링 브랜치(PR #18, gameStore slice 분리)가 끝나면 M2의 게스트 가드를
넣을 자리가 더 명확해지므로 **리팩토링 완료 후 착수 권장**.
