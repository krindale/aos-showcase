20년 차 웹 개발자 관점에서 실제 측정 데이터를 바탕으로 성능을 평가하겠습니다. 아키텍처는 Next.js(App Router) 정적 export를 GitHub Pages에서 서빙하는 구조이고, PWA(Service Worker + manifest)까지 붙어 있습니다.

측정 결과 요약

핵심 렌더링 지표는 매우 좋습니다. 홈 기준 TTFB 약 8ms, First Contentful Paint 약 52ms, DOMContentLoaded 17ms, load 완료 31ms로 나왔습니다. HTML은 gzip 36KB로 가볍고, DOM 노드 수도 홈 290개·맵 246개로 이상적인 수준입니다. 이 수치들은 정적 사이트 + Service Worker 캐시가 잘 맞물린 결과로, 재방문 시 사실상 즉시 로딩입니다. 결론부터 말하면 체감 성능은 이미 훌륭하고, 개선점은 "최초 방문자"와 "번들 다이어트"에 집중되어 있습니다.

강점

이미지 처리가 교과서적입니다. 맵 갤러리 11장 전부 WebP 포맷에 loading="lazy"가 적용되어 있고, 보드처럼 색이 많은 이미지를 PNG가 아닌 WebP로 낸 판단이 좋습니다. 아이콘류는 인라인 SVG(홈 이미지 요청이 사실상 PWA 아이콘 1개뿐)로 처리해 이미지 네트워크 요청 자체가 극히 적습니다. 모든 텍스트 리소스가 gzip으로 서빙되고, 웹폰트를 외부에서 불러오지 않아(폰트 요청 0건) 렌더 블로킹과 FOUT/FOIT 리스크가 없습니다. 라우트별 코드 스플리팅도 Next.js 기본대로 잘 동작하고 있습니다.

개선점

1) 캐시 정책이 가장 큰 아쉬움 (우선순위 최상)
모든 리소스가 cache-control: max-age=600, 즉 10분입니다. 그런데 _next/static/ 아래 파일들은 이름에 콘텐츠 해시가 박혀 있어(예: page-e4ded1d636dffef9.js) 내용이 바뀌면 파일명 자체가 바뀝니다. 이런 파일은 max-age=31536000, immutable(1년)로 줘도 안전한데 10분으로 묶여 있어, 캐시 만료 후 재방문 시 불필요한 조건부 요청이 발생합니다. 다만 이건 GitHub Pages의 고정 헤더라 직접 제어가 어렵습니다 — 헤더 커스터마이징이 필요하면 Cloudflare Pages나 Netlify로 옮기는 것이 근본 해법입니다. 지금은 Service Worker가 이 약점을 상당 부분 가려주고 있으니, SW 캐시 전략(해시 자산은 cache-first)을 확실히 잡아두는 것이 차선책입니다.

2) JS 번들 총량 (우선순위 상)
전체 JS 디코드 크기가 홈 기준 약 1.37MB, 프리페치까지 누적하면 약 2.7MB입니다. 개별 청크 중 fd9d1056...js(gzip 169KB), 117...js(122KB), 458...js(110KB)가 무겁고, 특히 게임 페이지 청크 page-e4ded...js는 디코드 434KB로 단일 파일 중 가장 큽니다. 게임 엔진 로직이 무거운 건 이해되지만, 홈·소개 페이지에서까지 이 부담이 프리페치로 딸려오는지 점검이 필요합니다. Next의 <Link prefetch={false}>를 소개 페이지 링크에 적용하거나, 게임 엔진을 dynamic(() => import(...), { ssr:false })로 지연 로딩하면 소개 페이지 방문자의 다운로드량을 크게 줄일 수 있습니다. 번들 분석기(@next/bundle-analyzer)로 어떤 라이브러리가 저 청크를 부풀리는지 한 번 열어보길 권합니다 — 보통 date/i18n/차트류 한두 개가 범인입니다.

3) 맵 이미지의 반응형 대응 (우선순위 중)
WebP·lazy는 잘 됐지만 srcset/sizes가 없어(sample 이미지에서 srcset 미설정 확인) 모바일에서도 데스크톱용 원본을 그대로 내려받습니다. korea.webp 280KB, germany.webp 210KB, rust-belt.webp 209KB 등 몇 장은 카드 썸네일 표시 크기에 비해 과합니다. Next의 next/image를 쓰거나 수동으로 2~3단계 크기의 srcset을 제공하면 모바일 데이터를 절반 이하로 줄일 수 있습니다. 갤러리 전체가 다 보일 때 이미지 합계가 1.5MB를 넘기므로 체감 효과가 있습니다.

4) CSS 번들 (우선순위 하)
CSS가 gzip 45KB로 HTML보다 큽니다. Tailwind로 추정되는데, 프로덕션 빌드에서 purge/content 스캔이 제대로 걸려 있는지 확인해볼 만합니다. 사용하지 않는 유틸리티가 남아 있으면 여기서 더 줄어듭니다. 단, 이건 렌더 블로킹 리소스이긴 해도 크기가 치명적이진 않아 우선순위는 낮습니다.

5) 측정·모니터링 관점
제가 잰 FCP 52ms는 캐시가 데워진 재방문 기준이라 실제 신규 방문자 경험과는 다를 수 있습니다. 정확한 판단을 위해 Lighthouse를 캐시 비활성/모바일 스로틀 조건으로 돌려 LCP·TBT·CLS를 확인하시길 권합니다. 특히 홈 히어로의 초대형 텍스트가 LCP 요소일 텐데, 폰트가 시스템/셀프호스트라 유리한 조건입니다.

정리

우선순위는 ① 정적 자산 캐시 수명 개선(호스팅/SW 전략) → ② 게임 엔진 청크 지연 로딩으로 소개 페이지 번들 다이어트 → ③ 맵 이미지 srcset 반응형 → ④ CSS purge 점검 순입니다. 이미 이미지·폰트·코드 스플리팅 같은 "큰 돌"은 잘 놓여 있어서, 남은 건 세밀한 튜닝 영역입니다.

원하시면 게임 엔진을 dynamic import로 분리하는 구체적인 Next.js 코드 예시나, Cloudflare Pages로 옮겼을 때의 _headers 캐시 설정 예시를 작성해드릴 수 있습니다. 어느 쪽을 더 깊게 볼까요?


- 윈도우 에서 특히나 느려짐

코드를 직접 파헤쳐 보니, Windows에서 느려지는 이유가 데이터로 꽤 명확하게 잡힙니다. Mac↔Windows 성능 격차는 거의 항상 "GPU 합성 부담"과 "폰트 렌더링" 두 축에서 갈리는데, 이 사이트는 그 두 가지에 정확히 해당합니다.

원인 1 — backdrop-filter: blur(12px) 유리 헤더 (가장 유력)

sticky 헤더에 backdrop-filter: blur(12px)가 걸려 있습니다(814×67 크기, 항상 화면 상단에 고정). 이게 Windows Chrome/Edge에서 느려지는 전형적 원흉입니다.

이유는 이렇습니다. backdrop-filter는 헤더 뒤에 있는 콘텐츠를 매 프레임 실시간으로 캡처해서 블러를 다시 계산합니다. 그런데 헤더가 sticky라 스크롤하는 내내 뒤 콘텐츠가 계속 바뀌므로, 스크롤 프레임마다 블러를 재연산합니다. Apple Silicon Mac은 통합 메모리 + 고도로 최적화된 Metal 백엔드 덕에 이걸 거의 공짜로 처리하지만, Windows는 GPU가 천차만별이고(특히 내장 그래픽 노트북) DirectX 합성 경로에서 backdrop blur 비용이 몇 배로 뜁니다. 같은 사이트가 M1 맥북에선 60fps, 인텔 내장그래픽 윈도우 노트북에선 스크롤이 뚝뚝 끊기는 대표적 시나리오입니다.

가장 효과 큰 개선은 이 블러를 조건부로 쓰는 것입니다. 블러를 반투명 단색 배경으로 대체하거나(background: rgba(...) + 낮은 투명도), 최소한 스크롤 중에는 끄고 멈췄을 때만 적용하는 방식, 혹은 @media (max-width: ...)나 성능 감지로 저사양에서 비활성화하는 방법이 있습니다. 디자인을 유지하고 싶다면 blur 반경을 12px에서 6~8px로만 낮춰도 Windows에서 체감 차이가 큽니다.

원인 2 — 웹폰트가 없어 OS별로 완전히 다른 렌더링

이게 두 번째 핵심입니다. 측정해보니 이 사이트는 웹폰트를 하나도 번들하지 않습니다(@font-face 규칙 0개, document.fonts.size === 0). CSS는 Space Grotesk(영문 히어로)와 IBM Plex Sans KR(한글 본문)을 지정하지만, 실제로는 둘 다 로드에 실패하고 시스템 fallback으로 렌더링되고 있습니다.

결과적으로 Mac과 Windows가 서로 다른 폰트로 다른 텍스트를 그리고 있습니다. Mac은 -apple-system(San Francisco) + Apple의 서브픽셀 렌더링으로 매끈하게 나오는 반면, Windows는 Segoe UI로 대체되고 DirectWrite 렌더링을 탑니다. 이건 성능보다 "일관성·가독성" 문제에 가깝지만, 사용자가 "윈도우에서 뭔가 이상하고 무거워 보인다"고 느끼는 인상에 크게 기여합니다. 특히 초대형 히어로 텍스트("Age of Steam")가 의도한 Space Grotesk가 아니라 대체 폰트로 나오면 자간·굵기가 틀어져 어색해집니다.

해결책은 Space Grotesk와 IBM Plex Sans KR를 .woff2로 셀프호스팅하고 font-display: swap으로 붙이는 것입니다. 한글 폰트는 용량이 크니 unicode-range로 서브셋(사용 글자만 추출)하면 됩니다. 이러면 OS와 무관하게 동일한 타이포그래피가 나오고, 지금처럼 폰트 요청이 0건이라 네트워크 부담도 크지 않습니다.

원인 3 — transition: all이 전역에 적용 (670개 요소)

게임 페이지에서 686개 요소 중 **670개에 transition-property: all**이 걸려 있습니다. 홈도 290개 중 278개가 그렇습니다. Tailwind의 transition 유틸리티나 전역 리셋에서 온 것으로 보입니다.

transition: all은 브라우저가 "이 요소의 어떤 속성이든 바뀌면 애니메이션 대상인지 매번 확인"하게 만듭니다. 레이아웃에 영향을 주는 속성(width, top, margin 등)이 트랜지션되면 그때마다 리플로우가 유발되는데, 이 리플로우 비용이 Windows에서 더 무겁습니다. 특히 게임 보드처럼 SVG 노드 168개가 있는 화면에서 상태가 바뀔 때 연쇄적으로 재계산이 일어날 수 있습니다. transition: all 대신 실제로 애니메이션할 속성만 명시(transition-property: transform, opacity, background-color)하도록 좁히는 것이 정석입니다. transform과 opacity는 GPU 합성만으로 처리돼 OS 간 격차가 가장 작습니다.

원인 4 — 게임 보드가 SVG 렌더링 (부차적, 대형 맵에서 주의)

게임 화면 보드가 canvas가 아니라 SVG로 그려지고 있습니다(SVG 37개, 벡터 노드 168개). 튜토리얼 맵은 헥스가 적어 괜찮지만, korea나 germany처럼 헥스·큐브·마커가 수백 개인 대형 맵에서는 SVG 노드 수가 폭증합니다. SVG는 각 노드가 DOM 요소라 노드가 많아질수록 스타일 재계산·페인트 비용이 노드 수에 비례해 늘고, 여기에 앞서 말한 transition: all과 box-shadow(게임 화면 31개)가 겹치면 Windows에서 상호작용이 눈에 띄게 느려질 수 있습니다. 대형 맵에서 인터랙션 지연이 심하다면, 정적 배경 레이어는 canvas나 단일 배경 이미지로 굽고 인터랙티브 요소만 SVG로 얹는 하이브리드 구조를 고려할 만합니다.

우선순위 정리

가장 적은 노력으로 큰 효과를 볼 순서로 보면, 먼저 ① backdrop-filter 블러를 제거하거나 반경을 낮추기 — Windows 스크롤 버벅임의 1순위 원인이고 수정도 CSS 몇 줄입니다. 다음으로 ② transition: all을 실제 속성으로 좁히기 — 인터랙션 반응성을 전반적으로 올려줍니다. 그다음 ③ 웹폰트 셀프호스팅 — 성능보다는 OS 간 시각적 일관성 문제지만 "윈도우에서 이상하다"는 인상을 없애줍니다. 마지막으로 ④ 대형 맵의 SVG 렌더링 최적화는 대형 맵에서 실제 지연이 확인될 때 손대면 됩니다.

한 가지 덧붙이면, 지금 진단은 제 환경에서 CSS 계산 결과를 분석한 것이라 "왜 느린지"의 원인 규명에는 신뢰도가 높지만, 실제 프레임 드랍 수치까지 재려면 문제가 나타나는 그 Windows 기기에서 Chrome DevTools의 Performance 탭으로 스크롤을 녹화해 "Rendering > Paint flashing"과 프레임 차트를 보시는 걸 권합니다. 특히 스크롤 중 헤더 영역이 초록색으로 계속 리페인트되는지 확인하면 backdrop-filter가 범인인지 1분 만에 검증됩니다.

원하시면 backdrop-filter를 성능 안전하게 대체하는 CSS 스니펫이나, IBM Plex Sans KR 서브셋 + @font-face 셋업 예시를 바로 작성해드릴게요.
