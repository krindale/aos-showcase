[트래픽 구조] 발생원 3가지
  - 상태 변경 스냅샷 : 변경 시마다 (debounce 120ms, 단계 전환은 1.2초 홀드)
                       → Realtime broadcast 1건 + rooms 테이블 UPDATE 1건
  - keepalive 재전송 : 5초 고정 (SNAPSHOT_KEEPALIVE), broadcast만
  - 하트비트         : 45초 (HEARTBEAT_INTERVAL), DB UPDATE만
  스냅샷 1건 크기 = gzip+base64 후 약 2KB (실측 최대 4,920 bytes)

[판당 소모] 4인 90분 기준 ※ 상태 변경 500회 가정한 추정
  - 상태 변경 500회 × 수신자 3 = 1,500 메시지
  - keepalive 1,080회 × 3      = 3,240 메시지
  - 합계 약 4,740 메시지 / egress 약 10MB → keepalive가 전체의 약 2/3

[무료 티어 여유]
  - 동시 접속 200명 ≈ 50개 방 / 메시지 200만/월 → 월 약 400판 (실질 병목)
  - egress 5GB/월 → 월 약 500판 / DB 500MB → 병목 아님 (방당 ~2KB 덮어쓰기)
  - 1주 미접속 시 프로젝트 자동 정지 ← 가장 먼저 부딪힘 (Pro에서 소멸)

[현재 이미 안전한 것 — 재작업 불필요]
  - 채팅 미저장 (broadcast만, DB에 안 남음) → 대화 내용 개인정보 이슈 없음
  - clientId = crypto.randomUUID (추측 불가) / Service Role Key 미노출 (anon만)
  - XSS: React 이스케이프 + dangerouslySetInnerHTML 미사용, 네이티브 다이얼로그 미사용
  - 입력 길이는 UI에서 캡 (이름 12·방제 20·코드 6~8자) ※ 단 서버 강제는 없음 → [S3]
  - pg_cron 방 자동 청소 (마지막 활동 6시간 경과 시 삭제, 하루 2회)
  - 호스트가 인텐트를 차례·좌석 기준으로 검증 ※ 단 발신자 위장은 가능 → [S2]

            ① 자기 uid로 방 생성 → 201        ② 남의 uid 위조 → 403 거부
            ③ 비참가자 update → 0건 차단      ④ 참가자 update → 성공
            ⑤ 승계(host_uid 갱신) → 성공      ⑥ 승계자가 방 닫기(delete) → 204
          ⑤⑥은 리뷰에서 고친 "승계 시 host_uid 갱신"이 없었으면 실패했을 경로다.

        ⚠️ 이제 **Anonymous sign-ins가 꺼지면 온라인이 전면 중단된다**(정책이 authenticated 전용).

     ⬜ S1b — select 조이기(별도): 지금 조이면 "코드로 방 찾기"와 "공개방 목록"이 함께
        죽는다. 목록용 뷰 + get_room_by_code security definer RPC + 클라이언트
        fetchRoom/listPublicRooms 교체가 한 묶음. 남는 노출은 정보 열람(비공개 방 코드·
        스냅샷 훔쳐보기)이고, 파괴적 조작은 3단계가 먼저 막는다.
     현재 정책(supabase/setup.sql) = 전부 허용형:
       rooms_select  using(true)  ← 비공개 방 포함 전 행 열람 가능:
                                     · 비공개 방 코드 열람 → 초대 없이 입장
                                     · seats의 clientId 열람 → 좌석 위장 재료
                                     · snapshot 열람 → 진행 중 게임 전체 훔쳐보기
       rooms_update  using(true)  ← 남의 방 스냅샷·좌석·호스트 조작 가능
       rooms_delete  (finished만) ← update로 status를 finished로 바꾼 뒤 삭제 가능
     방향: Supabase anonymous sign-in 도입 (사용자 체감상 로그인 화면 없음 —
           진입 시 자동 발급, 지금 sessionStorage clientId와 동일한 UX.
           무료 티어 MAU 5만이라 여유) 후:
       - select : is_public=true인 방만 + 민감 컬럼 제외한 목록 뷰
                  (snapshot·seats.clientId·비공개 코드는 목록에서 제외)
       - 코드 입장 : "코드 → 방" 조회를 security definer RPC로 (정확 일치만,
                  테이블 스캔으로 코드 수집 불가하게)
       - update/delete : 방 참가자(auth.uid가 좌석에 있는 사람)만,
                  호스트 교체·방 폐쇄는 호스트 uid만
     ※ clientId 처리 방침 확정(2026-08-01): **auth.uid 병행**.
        clientId(sessionStorage=탭별)는 좌석 식별용으로 그대로 두고, RLS만 uid로 판정한다.
        auth 세션은 localStorage(브라우저 공유)라 한 PC 두 탭이 같은 uid가 되는데,
        같은 사람이므로 문제가 없고 두 탭 테스트도 그대로 동작한다.

     ⚠️ 착수 전 반드시 읽을 것 — 2026-08-01 설계 중 발견한 함정 2가지:

     (1) **`host_uid = auth.uid()`로 update를 조이면 호스트 승계가 불가능해진다.**
         승계는 "게스트가 방 행을 update해서 host_client_id를 자기로 바꾸는" 동작이다.
         정책이 호스트만 허용하면 승계자는 영원히 권한을 못 얻어 방이 죽는다.
         → `participant_uids uuid[]` 같은 참가자 목록 컬럼이 필요하고,
           호스트가 좌석 배정 시 갱신하려면 claimSeat intent에 uid를 실어야 한다.
           즉 좌석 배정 경로 전체가 함께 바뀐다(roomLogic·netStore·transport).

     (2) **DB를 먼저 조이면 배포 전까지 온라인 기능이 전면 중단된다.**
         현재 클라이언트는 supabaseTransport에서 `persistSession: false`로 만들어져
         익명 로그인을 하지 않는다 → authenticated 기반 정책에 전부 걸린다.
         순서는 반드시 **클라이언트 코드 → 배포 → DB 적용**.
         또 Supabase 대시보드에서 Anonymous sign-ins를 먼저 켜야 한다
         (2026-08-01 확인: auth.users 0명 = 아직 미사용).

     GH Pages를 떠나야 하는 이유 3가지:
       ⓐ 약관 — GH Pages ToS는 "온라인 비즈니스 운영을 위한 무료 웹호스팅" 금지.
          도네이션을 받는 라이선스 계약 서비스는 위반 소지. 계약까지 마친 뒤
          호스팅 약관으로 내려가는 게 최악의 시나리오. (약관 원문 재확인 필요)
       ⓑ 보안 계층을 얹을 자리가 없음 — 커스텀 HTTP 헤더(CSP·noindex), WAF,
          rate limit, 봇 차단, 핫링크 방지가 전부 구조적으로 불가.
          → C2(robots)·C1(크롤링)·S4(남용)의 방어 수단이 여기에 묶여 있다.
       ⓒ private repo 배포에 유료 플랜 필요 — L2에서 repo를 private으로 돌리는
          선택지와 정면 충돌 (라이선스 대응과 호스팅이 서로 발목을 잡는다).

     후보 비교 (무료 티어 기준):
