온라인 서비스 공개 준비 — 조사 결과 및 할 일
조사일: 2026-07-29 (무료 + 도네이션 운영, 로그인 없는 서비스 전제)

════════════════════════════════════════════════════════════════
■ 측정된 사실 (추정치는 근거 표시)
════════════════════════════════════════════════════════════════

[트래픽 구조] 발생원 3가지
  - 상태 변경 스냅샷 : 변경 시마다 (debounce 120ms, 단계 전환은 1.2초 홀드)
                       → Realtime broadcast 1건 + rooms 테이블 UPDATE 1건
  - keepalive 재전송 : 5초 고정 (SNAPSHOT_KEEPALIVE), broadcast만
  - 하트비트         : 45초 (HEARTBEAT_INTERVAL), DB UPDATE만
  스냅샷 1건 크기 = gzip+base64 후 약 2KB (실측 최대 4,920 bytes)

[판당 소모] 4인 90분 기준 ※ 상태 변경 500회 가정한 추정
  - 상태 변경 500회 × 수신자 3 = 1,500 메시지
  - keepalive 1,080회 × 3      = 3,240 메시지
  - 합계 약 4,740 메시지 / egress 약 10MB
  → keepalive가 전체의 약 2/3

[무료 티어 여유]
  - 동시 접속 200명 ≈ 50개 방 (연결 한도)
  - 메시지 200만/월 → 월 약 400판   ← 실질 병목
  - egress 5GB/월  → 월 약 500판
  - DB 500MB       → 병목 아님 (아래 참조)

[DB 용량] 대시보드 25.78MB의 실제 내역
  - template0/template1  14.6MB  ← Postgres 고정 오버헤드, 손댈 수 없음
  - Supabase 내부 스키마 10.7MB  ← auth/storage/realtime 등, 안 써도 존재
  - rooms 테이블          0.25MB ← 우리 데이터 (방당 약 2KB, 스냅샷은 덮어쓰기라 누적 없음)
  → 남은 474MB로 방 9만 개 이상. 용량은 신경 쓸 필요 없음.

[가장 먼저 부딪힐 제약]
  1주 미접속 시 프로젝트 자동 정지 (대시보드에서 수동 재개)

════════════════════════════════════════════════════════════════
■ 할 일 (우선순위 순)
════════════════════════════════════════════════════════════════

[1] RLS 강화 — 공개 전 필수. 규모와 무관하게 시급
    현재 supabase/setup.sql:
      rooms_update           : for update to anon using (true) with check (true)
      rooms_delete_finished  : for delete using (status = 'finished')
    문제: anon 키는 브라우저에 노출됨 → 누구나 남의 방을 수정 가능.
          진행 중인 게임 스냅샷 조작, 좌석·호스트 변경, status를 finished로
          바꾼 뒤 삭제까지 가능. 친구 규모라 수용했던 설계(주석에 명시)지만
          공개하면 아무나 남의 판을 망칠 수 있다.
    방향: Supabase anonymous sign-in 도입 후 auth.uid() 기반 정책으로 교체.
          ※ 이건 사용자가 겪는 "로그인"이 아님 — 이메일·비밀번호·로그인 화면 없이
            진입 시 자동 발급. 지금 clientId를 sessionStorage에 넣는 것과 체감 동일.
            무료 티어 MAU 5만이라 도네이션 규모엔 여유.
    대안(로그인 개념도 없이): 방 생성 시 비밀 토큰 발급 → rooms에 저장하고
          수정 요청 헤더로 대조. 배관을 직접 만들어야 하고 토큰 유출 시 같은 문제.

[2] 방 생성 남용 방지
    현재 rooms_insert가 using(true) — 무제한 생성 가능. 스팸으로 공개방 목록을
    채우거나 DB를 부풀릴 수 있음. rate limit 필요.

[3] keepalive 조건부 전송 — 손해 없는 최적화 ★ 나중에 심도 있게 재검토하기로 함
    현재: safeInterval(5초)로 상태 변경과 무관하게 무조건 재전송.
          같은 payload라 게스트는 rev 가드(msg.rev <= lastAppliedRev)로 즉시 폐기.
          봇 차례(1.5초마다 갱신)에도 끼어들어 전부 중복.
          게임 종료 후 결과 화면에 머물러도 방 나갈 때까지 계속 돈다.
    수정: 같은 함수 바로 위에 이미 있는 lastBroadcastAt을 참조해
          Date.now() - lastBroadcastAt < SNAPSHOT_KEEPALIVE 이면 건너뛰기.
    효과: 활발한 구간 0회 / 정체 구간은 지금과 동일(5초) → 복구 지연 손해 없음.
          봇 게임 기준 판당 4,740 → 약 1,500 메시지, 무료 월 400판 → 약 1,300판.
    주의: 5초 interval에 조건만 붙이면 경계에서 최대 10초까지 벌어짐
          (t=4.9 스킵 → 다음 발사 t=9.9). 체크 주기를 1초로 두거나
          전송할 때마다 타이머 재설정할 것.
    ※ 참고: keepalive는 TCP/WebSocket 프로토콜 레벨이 아니라 애플리케이션 레벨
      재전송이다(Phoenix Channels broadcast). 연결 유지용 heartbeat는 별개로 돈다.

[4] 유실 빈도 실측 계측
    keepalive가 실제로 몇 번이나 게스트를 구제하는지 세는 지표가 없다.
    applySnapshotAsGuest에서 rev 점프(예: 5 → 8)를 카운트하면 유실 빈도를 알 수 있고,
    [3]의 판단 근거가 명확해진다.

[5] 치팅 대응 방침 결정
    호스트가 클라이언트라 상태 조작 가능 (docs에 "설계상 수용"으로 기록됨).
    공개 서비스에서 감수할지, 서버 권위로 갈지 결정 필요.
    구조가 net → store 단방향이라 net 계층만 교체하는 경로는 열려 있음.
