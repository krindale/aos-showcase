■ 측정된 사실 (추정치는 근거 표시)

[트래픽 구조] 발생원 3가지
  - 상태 변경 스냅샷 : 변경 시마다 (debounce 120ms, 단계 전환은 1.2초 홀드)
                       → Realtime broadcast 1건 + rooms 테이블 UPDATE 1건
  - keepalive 재전송 : 5초 고정 (SNAPSHOT_KEEPALIVE), broadcast만
  - 하트비트         : 45초 (HEARTBEAT_INTERVAL), DB UPDATE만
  스냅샷 1건 크기 = gzip+base64 후 약 2KB (실측 최대 4,920 bytes)

[판당 소모] 4인 90분 기준 ※ 상태 변경 500회 가정한 추정
  - 상태 변경 500회 × 수신자 3 = 1,500 메시지
  - keepalive 1,080회 × 3      = 3,240 메시지
  - 합계 약 4,740 메시지 / egress 약 10MB → keepalive가 전체의 약 2/3

[무료 티어 여유]
  - 동시 접속 200명 ≈ 50개 방 / 메시지 200만/월 → 월 약 400판 (실질 병목)
  - egress 5GB/월 → 월 약 500판 / DB 500MB → 병목 아님 (방당 ~2KB 덮어쓰기)
  - 1주 미접속 시 프로젝트 자동 정지 ← 가장 먼저 부딪힘 (Pro에서 소멸)

[현재 이미 안전한 것 — 재작업 불필요]
  - 채팅 미저장 (broadcast만, DB에 안 남음) → 대화 내용 개인정보 이슈 없음
  - clientId = crypto.randomUUID (추측 불가) / Service Role Key 미노출 (anon만)
  - XSS: React 이스케이프 + dangerouslySetInnerHTML 미사용, 네이티브 다이얼로그 미사용
  - 입력 길이는 UI에서 캡 (이름 12·방제 20·코드 6~8자) ※ 단 서버 강제는 없음 → [S3]
  - pg_cron 방 자동 청소 (마지막 활동 6시간 경과 시 삭제, 하루 2회)
  - 호스트가 인텐트를 차례·좌석 기준으로 검증 ※ 단 발신자 위장은 가능 → [S2]

■ P0 — 보안·권한 (공개 전 필수. 규모와 무관하게 시급)

[S1] RLS 전면 재설계 + 익명 로그인 ★ 최우선
     현재 정책(supabase/setup.sql) = 전부 허용형:
       rooms_select  using(true)  ← 비공개 방 포함 전 행 열람 가능:
                                     · 비공개 방 코드 열람 → 초대 없이 입장
                                     · seats의 clientId 열람 → 좌석 위장 재료
                                     · snapshot 열람 → 진행 중 게임 전체 훔쳐보기
       rooms_update  using(true)  ← 남의 방 스냅샷·좌석·호스트 조작 가능
       rooms_delete  (finished만) ← update로 status를 finished로 바꾼 뒤 삭제 가능
     방향: Supabase anonymous sign-in 도입 (사용자 체감상 로그인 화면 없음 —
           진입 시 자동 발급, 지금 sessionStorage clientId와 동일한 UX.
           무료 티어 MAU 5만이라 여유) 후:
       - select : is_public=true인 방만 + 민감 컬럼 제외한 목록 뷰
                  (snapshot·seats.clientId·비공개 코드는 목록에서 제외)
       - 코드 입장 : "코드 → 방" 조회를 security definer RPC로 (정확 일치만,
                  테이블 스캔으로 코드 수집 불가하게)
       - update/delete : 방 참가자(auth.uid가 좌석에 있는 사람)만,
                  호스트 교체·방 폐쇄는 호스트 uid만
     ※ clientId도 sessionStorage 자체 발급 → auth.uid 기반으로 통합 검토
        (F5 좌석 복원·두 탭 테스트 동작 유지 확인 필요)

[S2] Realtime 채널 보호 + 발신자 검증
     현재: 채널 이름 = 방 코드라 코드를 알면(=S1 전엔 누구나) 채널 참여 가능.
       ⓐ 게임·채팅 도청  ⓑ 위조 인텐트(clientId를 seats에서 읽어 위장 —
       호스트가 그대로 실행)  ⓒ 위조 스냅샷(netStore.onSnapshot이 발신자
       검증 없이 rev만 보고 적용 — 높은 rev로 쏘면 전 게스트 상태 오염)
     수정:
       - Supabase Realtime private channel + authorization (참가자만 join)
       - 앱 레벨 즉효약(선행 가능): 게스트는 snapshot 발신 clientId가
         room.hostClientId와 일치할 때만 적용, 호스트는 intent 발신 clientId와
         msg.clientId 일치 검증 (transport가 발신자 메타를 실어주면 됨)

[S3] DB 서버측 제약 — 클라이언트 캡은 우회 가능
     rooms에 check 제약 추가: title/이름 길이, seats 원소 수(≤6)·크기,
     snapshot 크기 상한(pg_column_size, 예: 256KB), code 형식([A-Z2-9]{6}).
     현재는 악의 클라이언트가 수 MB 방제·스냅샷 insert로 DB·목록 오염 가능.

[S4] 방 생성 남용 방지 (rate limit)
     현재 insert with check(true) — 무제한. 스팸 방으로 공개방 목록 마비 가능.
     방향: 익명 로그인 후 uid당 생성 빈도 제한 (trigger로 최근 N분 생성 수 검사)
           + 필요 시 Turnstile 같은 CAPTCHA를 방 생성에만 (플레이 UX 무영향).

[C1] 진짜 크롤링 타깃은 rooms API — S1이 곧 크롤링 방지다
     사이트 HTML보다 Supabase REST(rooms 전체 select)가 자동화 수집에 취약.
     S1 완료 시 "공개방 목록 뷰"만 긁을 수 있게 되어 실익이 사라짐.

[C2] robots.txt + meta robots — 현재 public/에 robots.txt 없음 (실측)
     - 쇼케이스 페이지(/, /gameplay, /actions, /maps)는 공개 후 색인 허용이 이득
     - /game/*, /online/*, /sfx는 Disallow + noindex (게임 화면·숨은 라우트가
       검색에 잡힐 이유 없음)
     - 라이선스 확정 전 공개 상태가 길어지면 사이트 전체 noindex도 검토
     ※ robots는 신사협정 — 악성 봇 차단은 C3의 몫.

[C3] GitHub Pages의 구조적 한계 → 프런트 교체 검토
     GH Pages는 커스텀 헤더·WAF·rate limit·봇 차단·핫링크 방지 전부 불가.
     퍼블릭 오픈 시 Cloudflare(무료) 프록시 or Cloudflare Pages 이전:
       봇 대응(Bot Fight Mode)·rate limit·캐시·커스텀 도메인·CSP 헤더 확보.
     맵 이미지 핫링크 방지도 여기서만 가능.

[O1] Supabase Pro ($25/월) — 1주 미접속 자동 정지 소멸 + 동접 500(125방).
     공개 서비스에서 "프로젝트 정지 = 전면 장애"라 무료 티어로는 공개 불가.
     사용량 알림(메시지/egress 80%) 설정.

[O2] keepalive 조건부 전송 — 손해 없는 최적화 (기존 조사 유지)
     lastBroadcastAt 참조해 최근 전송 있으면 스킵 → 판당 4,740 → 약 1,500
     메시지, 무료 400판 → 1,300판 (Pro면 3,000판+).
     주의: 5초 interval에 조건만 붙이면 경계에서 최대 10초 공백 —
     체크 주기 1초 또는 전송 시 타이머 재설정.

[O3] 유실 빈도 계측 — applySnapshotAsGuest에서 rev 점프 카운트.
     keepalive가 실제로 게스트를 구제하는 빈도 = O2 판단 근거.

[O4] 강퇴 실효화 — 현재 강퇴된 게스트가 코드로 바로 재입장 가능
     (claimSeat는 빈 좌석이면 배정). 방별 ban 목록(강퇴된 uid) 추가.

[O5] 닉네임·방제·채팅 최소한의 질서 — 공개 서비스 기본기
     금칙어 필터(이름·방제만이라도) + 방 내 신고/무시 기능은 후순위 검토.
     채팅은 미저장이라 사후 조치 불가함을 전제로 설계.

[O6] 에러 추적·가동 감시 — Sentry(무료 티어) + 업타임 모니터.
     현재 프로덕션 에러는 사용자 제보 외 알 방법 없음.

[O7] 이용약관·개인정보처리방침 페이지
     수집 항목이 사실상 없음(닉네임 세션 한정·채팅 미저장)을 명시하는 것
     자체가 신뢰 요소. 도네이션은 외부 플랫폼 약관 링크로 처리.
